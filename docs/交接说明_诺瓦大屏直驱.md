# 诺瓦 LED 大屏直驱 — 交接说明（2026-10-30 09:50）

> 新笔记本上的 Trae 打开本目录后，**第一句话就说**：`先读 交接说明_诺瓦大屏直驱.md，按「下一步」继续`。

## 1. 目标与当前结论

目标：用 4 台 RK3588 盒子替代诺瓦 V960 发送卡，直驱 1920×1080 的 LED 墙（每台驱动 480×1080 一列）。

当前结论（都已实测）：

| 结论 | 依据 |
|---|---|
| 屏体、接收卡、接线、拼接**无硬件故障** | 4 根网线插回 V960 后整屏完整、连续、在动 |
| 4 台盒子发送端本身**正常** | 各 30.0fps、每帧 1080 行包+1 场包、tx_errors=0、链路 1000Mb/s |
| 4 台盒子与屏体是**点对点直连**，中间没有交换机 | 用唯一目的 MAC 发送时其它盒子 eth0 接收计数为 0 |
| 诺瓦接收卡**会保留最后一帧**，停发不立刻黑屏 | 停发后画面定格 |
| **V960 重新初始化接收卡后再切回盒子，问题依旧** | 2026-10-30 09:43 实测：第1段在动、第2段残缺、第3/4段满屏但定格 |
| 每列能否锁定**带随机性**，重启服务会重新洗牌 | 多次重启出现不同组合（1+2 / 1+3+4 / 只有1） |
| 诺瓦 V960 **检测不到接收卡就不发流** | 拔线直连盒子抓包，两个口都是 0 个包 |

**⇒ 必须拿到 V960 的原始帧流做字节比对，才能定位差异。**

### 1.1 2026-11-02 更新（详见 `诺瓦单列直驱_4路验证总结.md` 第 8 节）

| 新结论 | 说明 |
|---|---|
| `nova-wall.service` 是开机自启的干扰源 | 它会用 `nova_desktop eth0 480 1080 50 17 0` 持续抢同一网口；之前盒子侧测试可能被污染。已 stop + disable，上机先确认 |
| 发送代码无差异 | Linux 与 Windows 实现逐字节一致（仅源 MAC、RGB/BGR 不同），"移植写错"可排除 |
| 时序已达标 | `SCHED_FIFO`+关 cpuidle 后包间隔 99.6% 在 15-19µs；`gap=16µs` 可稳定 50.0fps；再调 gap 无意义 |
| `PACKET_TX_RING` 不可用 | `send()` 返回 0 但 `tx_packets` 零增量，6 种组合全无效 |
| 抓包测量不可行 | `.27` 只有百兆；`.28` 的 `rx-usecs=327` 改不动；硬件时间戳数值非法 |
| 第 4 列几何异常（新） | 盒子驱动时画面呈多条竖向重复块，不像缺行；疑该列画布参数与 480×1080 不符，且该列尚未在笔记本方案下单独验证 |

⚠️ 做 P0 抓 V960 流时注意：**V960 检测不到接收卡就不发流**（文档第 1 节第 19 行实测）。所以不能用盒子串接替代接收卡，必须用交换机镜像或接收卡 OUT 口旁路。

## 5. 下一步：用交换机旁路抓 V960 原始帧流

前提：**接收卡必须在线**，V960 才发流，所以不能拔线直连，必须用交换机旁路（未知单播会被泛洪到所有端口）。

接法（只动第 2 列，其它列保持接在盒子上）：

1. 把接在 **.28 盒子**上的那根网线（通向第 2 列接收卡）拔下 → 插交换机 **2 号口**
2. **V960 第 2 口** → 交换机 **1 号口**
3. **.28 盒子网口** → 交换机 **3 号口**
4. **等 60 秒**（H3C 默认 STP 要 30 秒才放行）

抓包（在 .28 上，先停掉发送避免污染）：

```bash
sudo systemctl stop nova-wall && sudo pkill -x nova_desktop
sudo timeout 8 tcpdump -i eth0 -s 1600 -w /tmp/v960_port2.cap
```

（注意：**不要用 `pkill -f`**，模式串会匹配到执行它的 shell 自己，命令会自杀；用 `pkill -x`）

把 pcap 拉回本地解析：`py rk.py --host 172.20.32.28 ...` 只支持上传，取回需在 `rk.py` 里 `sftp.get`，或直接 `tcpdump -r` 打印前几包。

## 6. 要重点比对的东西

| 项 | 我们的发送端 | V960 实际 | 关注点 |
|---|---|---|---|
| EtherType | 0xFF00 | 待测 | 是否一致 |
| 目的/源 MAC | 12:34:56:78:9A:BC | 待测 | 4 口是否同一个目的 MAC |
| 包头 43 字节 | 34×00 + 7×55 + D5 09 | 待测 | **是否含端口号/数据组字段** |
| 行包 | 43 字节头 + 0x1E + 1440B，1498B | 待测 | 长度、行号字段 |
| 场包 | 0x2D，16 帧循环（00FF 序列/01FE/预留/全零） | 待测 | **实际内容与循环规律** |
| 帧结构 | 1080 行包 + 1 场包，突发 13ms | 待测 | 有无额外配置包、有无周期性初始化包 |

如果发现包头里有**端口号/数据组**字节，那基本就能解释"只有个别列能亮"：4 台盒子必须各自带不同的端口值。

## 7. 已知坑（别再踩）

- `pkill -f xxx` 会匹配到执行它的那条 shell 命令本身 → 一定用 `pkill -x`
- 重启盒子会清空 `/tmp`（放在 /tmp 的测试脚本/帧要重新上传）
- `/userdata/nuowa/*` 属主 root，必须 `sudo install` 覆盖
- 摄像头会重复输出约 18% 相同帧，判断"有没有在动"要用**间隔 10 秒以上的两帧做像素差**，不能只看一张
- 摄像头 AE 会自动曝光，亮度不可直接比较；左上方另有一块独立监视器（不是这面墙），比对时避开
- 60fps 这块屏吃不下（覆盖率仅 7%），30fps 是唯一可用档
- 频繁重启会把四列的锁定组合打乱，观察要静置几分钟
