## 2. 协议要点（诺瓦接收卡私有帧流）

```
以太网头 : dst 12:34:56:78:9A:BC   src = 网卡自身 MAC   EtherType 0xFF00
包头     : 43 字节 = 34×0x00 + 7×0x55 + 0xD5 + 0x09
行包     : 包头 + 0x1E + 1440 字节像素   → 总长 1498 字节，每行一包，无行号（按发送顺序对应）
场包     : 包头 + 0x2D + 1028 字节，16 帧循环（n%16 = 0..15）
每帧     : 1080 个行包 + 1 个场包 = 1081 包 = 1.56 MB
像素顺序 : RGB（发 (0,0,255) 显示蓝色，与卡莱特要求 BGR 不同）
```

场包 16 帧循环内容：

| n | 内容 |
|---|---|
| 0 | 1028B，`00 FF 00 FF` + 5..66 位置隔字节填 `00 FF` |
| 1 | 538B，首 4 字节 `01 FE 00 FF` |
| 2..7 | 1028B，首 4 字节 `n 00 00 FF` |
| 8..15 | 1028B 全零 |

## 3. 程序架构

### 3.1 视频播放 `nova_video_live.py`

三线程流水线，解码 / 建包 / 发送重叠，否则单帧建包 8ms + 发送 19.7ms 串行只能到 30fps：

```
ffmpeg 解码线程 ──► frame_q(4) ──► 建包线程 ──► send_q(2) ──► 发送线程 ──► eth0
```

| 组件 | 职责 |
|---|---|
| `decode_loop` | ffmpeg 输出 rgb24 rawvideo，按帧读取 |
| `build_loop` | 4 块 numpy 缓冲轮转，memcpy 像素 + 填场包 + 1081 次 `pcap_sendqueue_queue` |
| 主线程 | `pcap_sendqueue_transmit(sync=1)` + `precise_sleep` 帧节拍 |

### 3.2 静态图案 `nova_live.py`

预构建 16 个发送队列（每个对应一种场包），主循环直接轮转 `transmit`，不做逐帧建包，可顶到 60fps。

## 4. 关键参数

| 参数 | 值 | 说明 |
|---|---|---|
| 帧率 | **50 fps** | 单帧 19.7 ms vs 周期 20 ms，余量 1.3 ms |
| 包间隔 gap | **17 µs（自动）** | 1081 × 17µs = 18.4 ms 铺开，几乎铺满周期 |
| 带宽 | 622 Mbps（占千兆 62%） | |
| 分辨率 | 480 × 1080 RGB24 | 每帧 1.56 MB |
| 队列容量 | `n × (包长 + 512) + 场包 + 512 + 4096` | **必须加每包 512 字节**，否则入队失败 |

### 4.1 三条硬约束（实测得出，反直觉）

**① 接收卡要求数据流几乎铺满整个帧周期**

| gap | 每帧铺开 | 帧周期 | 结果 |
|---|---|---|---|
| 30 µs @30fps | 32.4 ms | 33.3 ms | ✅ 正常 |
| 28 µs @30fps | 30.3 ms | 33.3 ms | ❌ 丢锁 → 静止竖条纹乱码 |
| 18 µs @30fps | 19.5 ms | 33.3 ms | ❌ 丢锁 → 静止竖条纹乱码 |
| 17 µs @50fps | 18.4 ms | 20.0 ms | ✅ 正常 |

结论：**不能靠缩短铺开时间换余量**，空隙一大接收卡就丢锁。余量只能靠提升发送精度获得。

**② Windows `time.sleep` 精度约 15.6 ms**

`sleep(0.9ms)` 可能变成 15.6 ms，直接顶穿帧周期。必须「粗睡到距目标 2 ms + 忙等收尾」：

```python
def precise_sleep(target):
    while True:
        now = time.perf_counter()
        rem = target - now
        if rem <= 0:
            return
        if rem > 0.002:
            time.sleep(rem - 0.002)
```

**③ `--gap` 与 `--fps` 必须解耦**

只设 `--gap` 时，帧率会跟着包时间戳走（设 `--fps 30` 实跑 50fps）。主循环必须按 `t_start + sent/fps` 独立排节拍。

## 5. 踩过的坑

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 首次运行"入队失败" | Npcap 队列容量漏算每包 512B 外挂开销 | 容量公式加 512/包 |
| 2 | 设 50fps 只跑到 47.6 | `gap_us` 向上取整成 19µs，1081 包铺成 20.5ms 超出 20ms 周期 | 改向下取整 |
| 3 | `--fps 30` 实际跑 50 | 节拍只由包时间戳决定 | 主循环加独立帧节拍 |
| 4 | 偶发闪（每约 20 秒一次） | 单帧耗时出现 34–38ms 尖峰 > 周期 | `precise_sleep` 忙等定时 |
| 5 | 整列黑 / 竖条纹乱码 | 帧间空隙过大，接收卡丢锁 | gap 必须铺满周期 |
| 6 | `You don't have permission` | Npcap 装了 Admin-only Mode | 重装时取消勾选该项 |
| 7 | 网卡句柄占用，后续打不开 | 强杀进程未释放 | 用 `.stop_send` 正常退出 |
| 8 | 误判"不闪" | 只查黑行占比，把静止乱码当成正常 | 必须同时算帧间像素差（<0.5 记为静止） |

### 6.4 移植实测结果（2026-10-30）

**笔记本端：全部通过**（第 1–4 列均已验证，见第 1 节）。

**RK3588 端：未通过**。2026-10-30 排查结论：

同一根线、同一接收卡、同一时刻，笔记本发 calib 图案显示完全正确的六色条带，切到 172.20.32.31 后无论怎么调都不显示（全黑或只显示底部少量行）。逐项排除如下：

| 排查项 | 方法 | 结果 |
|---|---|---|
| 包格式 / 包长 / EtherType | tcpdump 抓包逐字节比对 | ✅ 与笔记本完全一致（dst `12:34:56:78:9a:bc`、0xff00、43 字节头、0x1e、1498B） |
| 包间隔 | tcpdump -ttt 测间隔 | 20fps + gap46µs 时 45/46/46/46µs **完全均匀**，仍不显示 |
| 源 MAC | 把 eth0 MAC 改成笔记本的 `10:b6:76:42:42:8e` | ❌ 无效 |
| 链路 | operstate / carrier / speed | ✅ up / 1 / 1000Mbps |
| offload | tx-checksumming、scatter-gather、tso、gso、gro 全关 | ❌ 无效 |
| 网卡计数 | ethtool -S / ip -s link | TX errors 0 / dropped 0 / underflow 0 |
| 接收卡状态 | 同一根线换笔记本发 calib | ✅ 六色条带完全正确 |
| 二进制 | strings + md5 比对源码 | ✅ 一致（仅 NOVA_PHASE_MS） |
| 发送方式 | 逐包 sendto / slot_ns / 整帧 sendmmsg / 8 包批量 | 全黑 / 全黑 / 竖条纹错位 / 只显示底部一条 |

**剩余唯一可疑方向：Linux 用户态发包精度不足。**

- 逐包 `sendto` 单次系统调用 20–50µs，而 50fps 需要 17µs/包、30fps 需要 30.8µs/包 —— 都追不上，包在驱动队列积压后突发弹出（实测间隔 4–52µs 乱跳）
- `sendmmsg` 整帧提交能加快，但网卡按线速（12µs/包）连发，接收卡缓冲溢出导致行错位
- 本内核不支持 TC 的 `tbf` 整形（`RTNETLINK answers: Operation not supported`），无法用流控平滑

**下一步可选方案**（按代价排序）：

1. **PACKET_TX_RING**（mmap 环形缓冲 + 内核侧提交）—— 绕开逐包系统调用，可达微秒级发包间隔，是最可能成功的方案
2. XDP / AF_XDP —— 更激进，需要驱动支持
3. 换 USB 千兆网卡（RTL8153 等）—— 驱动模型不同，未验证
4. **保留笔记本方案**（已验证 4 路可用），RK3588 仅作管理/解码节点

> 注：`NOVA_SENDER_GAP_US` 填 `-1` 会让 nova_desktop 自动算出 18.5µs（正好铺满 20ms 周期、无余量），实测掉到 46.4fps，不可用；但这属于次要问题，主因是发包精度。



## 7. V960 初始化依赖（已实测确认）

### 7.1 三组对照实验

| # | 条件 | 结果 |
|---|---|---|
| 1 | 接收卡保持通电，仅换发送端为笔记本 | ✅ 四路全部点亮并播放 |
| 2 | 屏体断电 10 秒后重新上电，**直接用笔记本发** | ❌ 全黑，重试重启发送仍全黑 |
| 3 | 断电后先接 V960 把该列点亮，再切回笔记本 | ✅ 立即恢复，12 秒 300 帧活动率 100% |

### 7.2 结论

**接收卡断电重启后，必须先由原厂设备（V960 / NovaLCT）初始化一次，之后才接受第三方数据流。**

- 接收卡的屏体配置与「接受私有帧流」的许可状态驻留在卡内易失存储，断电即丢失
- 第三方发送端只能推像素数据，**无法写回这份配置**
- 一旦被 V960 重新初始化，配置恢复，第三方又可正常驱动（且掉电前一直有效）

### 7.3 对 RK3588 方案的直接影响

这是**唯一会阻断无人值守**的点：RK3588 方案是「断电自恢复」，但如果屏体和盒子共用一路电源，断电时接收卡配置一并丢失，重启后盒子发什么都没用。

| 部署方式 | 断电后是否需要人工介入 |
|---|---|
| 屏体与 RK3588 共用电源 | **需要**：先接 V960 点亮一次，再切回盒子 |
| 屏体与 RK3588 独立供电，仅盒子重启 | 不需要（接收卡未断电） |

### 7.4 推荐的恢复流程（四路一次做完）

1. 把 4 根网线**全部**插到 V960 的 4 个输出口
2. 给屏体上电，等 V960 把四列全部点亮（一次完成四列初始化）
3. 逐根拔下，分别插到 4 台 RK3588 的 eth0
4. 启动 `nova-wall` 服务，四列自动接管

⚠️ 关键：**不要只初始化其中一列**。断电时四列配置全部丢失，必须四列一起初始化。

⚠️ 拔线后接收卡会保留配置，不会因为换发送端而失效（实验 1、3 已验证）

## 8. 2026-11-02 补充：RK3588 的结构性阻断（结论：暂不可行）

本节记录一轮系统性复测，结论是**RK3588 直驱在这块板子 + 这颗内核上无法完成**，原因不在发送代码，而在内核与驱动的能力边界。以下每条都是实测，不是推断。

### 8.1 先修正一个历史干扰源

`nova-wall.service` 是 `enabled` 且开机自启，会执行 `nova_desktop eth0 480 1080 50 17 0` 持续发视频。**之前所有盒子侧的测试都可能与它抢同一个网口**（同一个 eth0、同一个目标 MAC）。现已 `systemctl stop` + `disable`。

> 以后每次上机，第一件事确认：`ps -ef | grep nova_desktop` 与 `systemctl is-enabled nova-wall.service`。

### 8.2 发送代码本身没有差异（已由代码审查确认）

`nova_desktop.c`（Linux）与 `nova_live.py` / `nova_video_live.py`（Windows）逐项比对：

| 项目 | 结果 |
|---|---|
| 目的 MAC / EtherType / 15 字节前缀 / 43 字节协议头 | 逐字节一致 |
| 类型字节 0x1E / 0x2D 的位置（偏移 57）、payload 起点（偏移 58） | 一致 |
| 每帧 1080 行包 + 1 场包、场包在最后、16 种场包按 `frame_no%16` 轮转 | 一致 |
| 行包 payload 1440 字节、1498 字节/包、480×1080 stride=1440 | 一致 |
| 源 MAC | 唯一差异（动态读网口 vs 硬编码），已验证改 MAC 无效 |
| 像素顺序 | 唯一差异（Linux 收 RGB24，`nova_live.py` 发 BGR），只影响红蓝互换，不影响覆盖范围 |

**所以"移植写错了"这条线可以关掉。**

### 8.3 发送端时序：已能做到精确 50.0fps

| 配置 | 实测 | 屏上结果 |
|---|---|---|
| `SCHED_FIFO 99` + 绑 A76 核 + 关全部 cpuidle | 包间隔 15–19µs 占 86%，<5µs 突发占 10%，30–100µs 卡顿占 4% | 只有底部一条 |
| 追加"卡顿超过 25µs 就重对齐、不追包"（`NOVA_NOCATCH`） | 15–19µs 占 **99.6%**，突发基本消失 | 只有底部一条 |
| `gap=17µs / 50fps` | 48.2fps（读帧+逐行拷贝压在周期外） | 只有底部一条 |
| `gap=16µs / 50fps` | **50.0fps** | 只有底部一条 |
| `gap=12µs / 50fps` | **50.0fps** | 曾出现整列彩色画面一次，随后复测全黑，不可复现 |
| `gap=0`（整帧连发）/ 30fps | 37.9fps（逐包 sendto 约 24µs/包 ≈ 500Mbps，一帧要 26ms） | 整列彩虹渐变 + 竖向错位 |

**结论：帧率与时序指标已经达标，再调 gap 没有意义。**

### 8.4 三条被硬件/内核堵死的路

| 方案 | 实测结果 |
|---|---|
| `PACKET_TX_RING`（TPACKET_V2 整帧灌环） | `send()` 返回 0、无报错，但 `tx_packets` **零增量**，`tp_status` 永远停在 `TP_STATUS_SEND_REQUEST=1`。3 种 kick（send / sendto / write）× 开关 `PACKET_QDISC_BYPASS` 共 6 组全部无效 → **该内核 TX 环路不可用** |
| `SO_TXTIME` + ETF 内核定时推包 | `CONFIG_NET_SCHED is not set`，`tc qdisc` 直接 `Operation not supported`，`modprobe sch_etf` 无此模块 → 必须重编内核 |
| 重编内核 | 华北工控不外发 BSP；公开 rockchip 树是 5.10.252，本机是 5.10.226-**gd4e939e1bf68**（该 commit 不在公开树）；内核在独立 boot 分区，刷坏需 maskrom 救援 |
| 改网卡参数提吞吐 | `ethtool -G eth0 tx 1024` 前后整机重启一次（`uptime` 归零、`/tmp` 清空）；`ethtool -C rx-usecs 0` 在 st_gmac 上不生效（仍为 327） |

另有一条实测风险：这块板子**会自行重启**（当天两次），重启即清空 `/tmp`，所以测试脚本与测试帧必须放 `/userdata`。

### 8.5 抓包测量这条路也不通

想用第二个盒子做旁路抓包，实测：

| 抓包点 | 结果 |
|---|---|
| 172.20.32.27 eth0 | 只支持 10/100M，与 .31 协商成 100Mbps，发送端直接被压到 **7.6fps**，不能测 |
| 172.20.32.28 eth0（千兆） | `rx-usecs=327` 且 `ethtool -C` 改不动 → 时间戳被攒批，10500 个间隔里 10250 个落在 0-5µs |
| `tcpdump -j adapter_unsynced` 硬件时间戳 | 算出的平均包间隔 4.4µs（1Gbps 下物理不可能），**数值不可信** |

### 8.6 第 4 列的几何异常（新观察）

盒子驱动时，屏上不是"缺行"，而是**画面被切成多条竖向重复块**：8 色带帧显示成若干条竖向色条；横向灰度渐变帧显示成明暗不同的竖条，且只占该列高度的一部分。同类现象在 `gap=12µs` 那次"整列彩色"画面里也出现过（约 8 条竖块）。

这一条**不是时序能解释的**，更像该列接收卡的画布/宽高参数与 480×1080 对不上（或该列从未在笔记本方案下单独验证过）。**这是目前唯一还没有被验证过的变量。**

2. **P0' · 用笔记本单独验证第 4 列**：笔记本接第 4 列 IN，发同一张 8 色带帧。若笔记本显示也不对 → 该列配置问题（需 NovaLCT 重设），与盒子无关；若笔记本正常 → 仍是盒子/驱动问题。
3. **P1 · 工程落地**：先恢复笔记本 4 路 50fps 保证现场可用。
4. **P2 · 盒子的前置条件**：拿到华北工控 BSP 源码（重编内核开 `NET_SCHED`+`ETF`）或加 Intel i210/i225（硬件 Launch Time），否则不建议再投入。
