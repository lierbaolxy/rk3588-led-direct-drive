# RK3588 LED 大屏直驱（诺瓦 / 卡莱特）

用 RK3588 替代原厂发送卡（卡莱特 S6F、诺瓦 V960），通过板载千兆网口**点对点直连接收卡**，直接推送 LED 私有协议的原始二层帧流。

本仓库同时包含两套协议的完整逆向结果、可用发送端、部署文档，以及从「完全点不亮」到「8 列 60fps 帧级同步」全过程中踩过的坑和对应解法。

## 1. 效果与现状

| 项 | 卡莱特侧 | 诺瓦侧 |
|---|---|---|
| 设备 | 4 × RK3588（EMB-3582） | 4 × RK3588（EMB-3582） |
| 单路分辨率 | 480 × 1080 | 480 × 1080 |
| 发送帧率 | 59.94 / 60 fps | 60 fps |
| 单路带宽 | 758–759 Mbps | 约 758 Mbps |
| 发送方式 | 用户态 AF_PACKET（`rk_send.py`） | **自写内核模块**（`nova_kmod.ko`） |
| 同步方式 | chrony + 固定 epoch + 墙钟时隙 | 同左 + 内核发送相位锚定 |

8 列横向拼成 3840 × 1080。稳态下 8 台内容帧差 0 帧、发送相位统一为 `4541µs`，NTP 偏差 <0.35ms。

### 2.2 接线要点

- 每台盒子 **一根网线直连接收卡的 IN 口**，点对点，中间**不要过交换机**。
- 发送口是 `eth0`，**不配 IP**，走原始二层（AF_PACKET / 内核直接下发）。
- 管理通道走 `wlan0`（或板载 `eth1`），与 LED 数据口物理分离，避免管理流量干扰 16.7ms 节拍。
- `.177` 同时充当全网 NTP 主时钟（`local stratum 10`），其余 7 台 chrony 指向它。
- 接收卡本身不需要改配置：**不要发送布局配置包**（诺瓦 `0x02`、卡莱特同类包），否则会覆盖 LEDSetting 里的箱体映射。

## 3. 两套协议的关键差异

这部分是整个项目最核心的认知，也是「卡莱特三天上线、诺瓦打了十天」的原因。

| 项 | 卡莱特（S6F 逆向） | 诺瓦（V960 逆向） |
|---|---|---|
| EtherType | `0x55xx` | `0xFF00` |
| 目的 MAC | `11:22:33:44:55:66` | `12:34:56:78:9A:BC` |
| 协议头 | 7 字节 | **43 字节**（`34×00 + 7×55 + D5 09`） |
| 行包长度 | 1461 B | 1498 B |
| 类型字节 | `0x55` | `0x1E`（行包）/ `0x2D`（场包） |
| **行号** | **包内有行号字段（偏移 13–14）** | **没有行号，靠到达时刻推断** |
| 场/同步包 | 1036 B，帧尾发送，第 14 字节为帧计数器 | 1028 B，16 帧循环 |
| 像素顺序 | **BGR** | **RGB** |
| 每帧包数 | 1081（1080 行 + 1 同步） | 1081（1080 行 + 1 场包） |
| 停发行为 | 立即黑屏 | **保留最后一帧（定格）** |

**结论：卡莱特可以用普通用户态程序稳定驱动；诺瓦不行。** 诺瓦把「行号」编码进了**时间**里——第 n 个包在什么时刻到达，就代表第 n 行。所以发送节拍不是性能优化项，而是**协议的一部分**。

## 5. 快速开始

### 5.1 诺瓦侧

```bash

cd /userdata/nuowa/kmod
PATH=/tmp/pybin:$PATH make -C /userdata/nuowa/kernel-build/kernel-ae667fd0b2e0ca9f85e8cdba745ac2a8c621eb65 M=$PWD modules

# 2) 加载并起播
sudo insmod nova_kmod.ko
sudo env NOVA_KMOD=1 NOVA_KMOD_CPU=6 \
    NOVA_CROP_X=480 NOVA_SYNC_EPOCH=1767196800 \
```

## 6. 硬性工程约束

这些不是经验值，是实测边界，违反任一条都会直接黑屏或丢锁。

1. **诺瓦数据流必须铺满帧周期**：60fps 用 `gap=15µs`，铺开约 16.2ms / 16.667ms（约 97%）。空窗超过 1–3ms 接收卡立刻丢锁，画面定格成竖条纹乱码。
2. **诺瓦行包没有行号**，发包时刻抖动 = 行错位；这就是用户态 `sendto`/`sendmmsg`/`PACKET_TX_RING` 全部失败的根因。
3. **诺瓦接收卡断电会丢「接受第三方帧流」许可**，必须先由 V960/NovaLCT 初始化一次；只拔线换发送端不会失效。
4. **刷新率档位在 NovaLCT 里**：这批卡原配置只认 30Hz，32/35/40/48fps 实测全部异常；60fps 是先改卡配置才成立的。
5. **卡莱特像素是 BGR，诺瓦是 RGB**，两者相反，写发送端时注意别互换。
6. **不要发布局配置包**，会覆盖接收卡里由 LEDSetting 配好的箱体映射。
7. **每台只能有一个发送进程**，两个进程抢同一个 eth0 会导致每帧都追不上。
8. **CPU 必须满频（performance）**，`ondemand` 低频下 16.7ms 内发不完 1.58MB，会退化成 30fps。
9. **网卡 EEE / offload / 流控必须关闭**，否则细密频闪或丢包。
10. **SCHED_FIFO 忙等必须配 `sched_rt_runtime_us=-1`**，否则每秒被踢出 CPU 一次，形成固定节奏闪黑。
11. **全局同步三把锁**：`epoch=1767196800`、周期精确 `1/60s`（不是 16.667ms 小数）、总帧数 8 路完全一致。改任一把立刻失步。

## 7. 踩坑与解决

完整台账见文档，这里挑影响最大的。

### 7.1 诺瓦侧

| 现象 | 根因 | 解法 |
|---|---|---|
| 画面全黑 / 竖条纹 / 只有底部一条 | 用户态发包节拍追不上 15–30µs，包在驱动队列积压后突发弹出 | 自写内核模块，内核态逐包绝对时刻忙等 + `dev_direct_xmit` |
| `PACKET_TX_RING` 无报错但零发包 | 该内核 TX 环路不可用，`tp_status` 永远停在 SEND_REQUEST | 放弃，改走 LKM |
| `SO_TXTIME` + ETF 不可用 | 内核未编 `NET_SCHED`，`sch_etf` 不存在；BSP 不对外 | 不再走内核本体，改用可加载模块 |
| 模块 insmod 返回 0 但 init 不执行 | 用 vanilla 内核源码编译，Rockchip/Android 改过 `struct module` 布局 | 必须用 Rockchip 5.10.226 源码 + 目标机配置构建 |
| 早上三台同时卡死，杀不掉、卸不掉 | `submit` 等空帧槽用无超时 `wait_event`，进程进 D 状态 | 加 12ms 超时返回 `-EAGAIN`，连续超时退出并由 systemd 自愈 |
| 进程仍偶发卡在 D 状态 | 卡在 `alloc_skb → drain_all_pages → flush_work`，被 CPU6 的 RT 忙等线程拖住 | 目前只能整机重启；见第 9 节 |
| 启动瞬间狂补发风暴 | `resend` 数组已分配导致 `!ctx->resend` 判空失效 | 改判 `!ctx->resend || !ctx->resend_count` |
| 帧尾释放 skb 挤占空档导致丢锁 | 帧尾成批释放占用 0.9ms | 延迟释放队列 + 10ms 边界钳制 |
| 四路画面帧号对齐但相位漂 | 发送按进程启动时刻累加，四台各自为政 | 相位锚定：每帧起点取 `epoch + ceil((now-epoch)/period)*period` |
| 补发时接缝错位 | 补发决策点 8ms 太早，`submit` 复制 1080 个 skb 常超 4ms | `DECIDE_NS` 收到 3ms |
| 帧槽不够，抖动时误补发 | 缓冲深度不足 | 帧槽 3 → 5，预填 1 → 2 帧 |

### 7.2 卡莱特侧

| 现象 | 根因 | 解法 |
|---|---|---|
| 首次运行入队失败 | Npcap 队列容量漏算每包 512B 外挂开销 | 容量公式加 512/包 |
| 设 50fps 只跑 47.6 | `gap_us` 向上取整，铺开超过周期 | 向下取整 |
| `--fps 30` 实际跑 50 | 节拍只由包时间戳决定 | 主循环加独立帧节拍 |
| 某块持续闪烁 | 同机跑了两个发送进程抢网口 | 起播前确认进程数 = 1 |
| 重启后速率只有 380Mbps | CPU 调频回落 `ondemand` | `performance` 写进启动脚本 |
| 自启服务 exit 127 | 脚本是 CRLF 换行，bash 把 `true\r` 当命令 | 转 LF + `bash -n` 校验 |
| 某块整体偏 1.1 秒，重启不消 | RTC 快了 1.145s，chrony 步进后内容相位永久超前 | 时钟闸门查 `Reference ID=AC1421B1` 且偏差 <5ms 才起播 |
| 起播对齐、十几分钟后散 | `-ss` 与 `-stream_loop` 同用，循环不回文件头 | 循环自己管，每遍从 0 起播 |
| 反复重启后相位错开 2 分钟 | 各台用 `date +%s` 现场算 T0，跨分钟边界产生竞态 | 固定常量 T0，内容位置做成墙钟的纯函数 |

## 8. 怎么验证画面

不要用「黑行占比」单一指标下结论，静止的乱码也会被判成正常。

1. **最少两张间隔 ≥3 秒的快照**，确认内容确实在变。
2. 拿不准时用 **RTSP 录 15–20 秒逐帧分析**。
3. 必须同时满足三条才算正常：**画面在动 + 无缺行 + 非静止乱码**。
4. 判据不满足时如实报告现象，不要含糊说「基本正常」。

仓库里的 `rtsp_*.py` 就是这套判据的实现（摄像头地址通过 `LED_CAM_URL` 传入）。

## 9. 已知限制

1. **诺瓦补发率随负载上升**：早上 6–14 次/分，负载高时 27–34 次/分。`python` 供帧接近 86%、`ffmpeg` 解码 41%，边界前 16ms 窗口被压缩。
2. **诺瓦发送端存在低频 D 状态卡死**：进程可能卡在内核内存回收路径（详见 9.1），现有 12ms 超时兜不住，只能整机重启。建议加外部看门狗。
3. **时间源单点**：全网只有 `.177` 一个 NTP 源，长时间离线会累积偏差。
4. **画面比例**：4K 16:9 源铺满 32:9 屏，按需求做了垂直压缩，人物会显矮胖。
5. **8 等份 vs 4 等份**：8 等份会带来垂直压缩 + 接缝翻倍，且解码/传输负载上升，观感不如 4 台各带完整画面。

### 9.1 故障实例：第 2 路无画面（2026-11-11）

**现象**：断电重启后第 2 路（`.28`，全屏第 6 列）无画面，其余七路正常。

**排查**：

| 观察 | 推断 |
|---|---|
| `.27/.30/.31` uptime 2 分钟，`.28` **uptime 6 天** | 这一台没随断电重启，仍带着六天前的旧进程 |
| dmesg：约 6 天前 `eth0: Link is Down`，今天才 `Link is Up` | 网口曾掉链近 6 天，期间像素流一包都发不出去 |
| `tx_dropped` 累计 326 亿、`发送错` 累计 23 亿 | 断链期间每个包都在失败 |
| 进程 `STAT=D`，`/proc/PID/stack` 为 `__flush_work → drain_all_pages → __alloc_pages_nodemask → __alloc_skb` | 卡在 skb 分配的内存回收，**不是** `submit` 的 `wait_event` |
| 日志与 `补发` 计数停止更新，但 `tx_packets` 仍在增长 | 用户态已停摆，内核 TX 线程仍在按帧发送 |

**根因**：链路长时间中断后，`alloc_skb` 触发 `drain_all_pages`，它需要 `flush_work` 等 per-CPU workqueue；而 CPU6 被 SCHED_FIFO 忙等发送线程占满，workqueue 得不到调度，形成永久不可中断等待。`NOVA_TX_SLOT_WAIT_MS=12` 只覆盖 `submit` 等空帧槽，覆盖不到内存分配路径，因此自愈没有生效。

**处置**：`systemctl stop` 后服务变 `failed`，但进程仍是 `D`、模块引用计数为 1 无法 `rmmod`，只能整机重启。重启后 60fps、`相位=4541µs`、`tx_errors=0`，与其余七路一致。

**改进方向**：

- 外部看门狗：日志超过 10 秒不更新就重启服务（需先实测 D 状态下 `reboot` 是否仍可用）。
- 链路守护：`carrier` 掉线时直接停服务，避免长时间无效发送把内存回收路径拖死。
- 内核侧：帧缓冲区改为预分配复用，避开高频 `alloc_skb` 路径。
